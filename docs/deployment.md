# Deployment Guide

## 1. Neon (database)
1. Create a project and a database.
2. Copy the **pooled** connection string (the host contains `-pooler`).
3. It should end with `?sslmode=require`.
4. Save it as `DATABASE_URL`.
5. Keep the app's pool small (`max: 3`).
6. Cold start: after idle, the first query is slow. Add a short connect retry (2-3 tries) and show a loading message in the UI.

## 2. Cloudinary (images)
1. Create a free account.
2. From the dashboard copy the **cloud name**, **API key**, and **API secret**.
3. Optionally create an upload folder (for example `inventory/`) and use it in the signature.
4. Only the cloud name and API key are safe to expose to the browser. The secret stays on the server.

## 3. Root scripts (already in the repo's `package.json`)
`--include=dev` on the client matters: Render sets `NODE_ENV=production` during the build, which would otherwise skip `vite` and fail the build.
```json
{
  "scripts": {
    "dev": "concurrently \"npm run dev --prefix server\" \"npm run dev --prefix client\"",
    "build": "npm install --prefix server && npm install --prefix client --include=dev && npm run build --prefix client",
    "start": "node server/src/index.js",
    "migrate": "npm run db:migrate --prefix server",
    "seed": "npm run db:seed --prefix server"
  }
}
```

## 4. Render (hosting)
Create one **Web Service** from your GitHub repo.

| Setting | Value |
|---|---|
| Runtime | Node |
| Build command | `npm run build` |
| Start command | `npm start` |
| Health check path | `/health` |
| Plan | Free |

The service is defined in `render.yaml` at the repo root (a Render Blueprint). Check `region` there first: it should match your Neon region and cannot be changed after the service is created.

`sync: false` means you enter the value in the Render dashboard, so it never lives in git. `JWT_SECRET` is generated by Render. Do not set `CLIENT_ORIGIN` on Render (same-origin).

## 4a. First deploy (task 64)
1. On GitHub create a **private** empty repository (no README, no .gitignore).
2. From the repo folder: `git remote add origin https://github.com/<you>/<repo>.git`, then `git push -u origin master`. The branch is `master`; keep that name or change it in Render.
3. In Render choose **New > Blueprint**, connect GitHub, pick the repo. Render reads `render.yaml` and asks for the four `sync: false` values (task 65): `DATABASE_URL`, `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`. `JWT_SECRET` is generated for you.
4. Run the migration against Neon **before or right after** the first deploy (section 5); the app boots without tables but every login fails until they exist.
5. Open `https://<service>.onrender.com/health`: it should say `ok`. Then open `/login`.
6. If the build fails, the log names the cause; see section 9. The most likely ones are a missing env var or a wrong `DATABASE_URL`.

## 5. Run the migration
Run once from your own machine against Neon (set `DATABASE_URL` locally first):
```
npm run migrate
npm run seed      # optional demo data
```
Re-run `migrate` whenever the schema changes, before deploying the new code.

## 6. Uptime bot
- Tool: UptimeRobot or cron-job.org.
- URL: `https://<your-app>.onrender.com/health`
- Interval: every 5-10 minutes.
- `/health` must **not** query the database, so Neon can still scale to zero.

## 7. Backups (weekly `pg_dump`)
The workflow is `.github/workflows/backup.yml` (Sundays 03:00 UTC, or run it by hand from the Actions tab).

Setup, in GitHub under Settings > Secrets and variables > Actions:
- **Secret `BACKUP_DATABASE_URL`**: the Neon **direct** (non-pooled) connection string, ending `?sslmode=require`.
- **Variable `PG_VERSION`** (optional): your Neon project's Postgres major version. Default is 17. `pg_dump` must be the same version or newer than the server, or it refuses to run.

Then run it once by hand and confirm a green run with a `db-backup` artifact.

Things to know:
- Artifacts hold all customer data and are visible to anyone with repo access: keep the repo **private**.
- Artifacts expire after 30 days, so the newest backups are always 1 to 4 weekly files.
- GitHub turns scheduled workflows off after 60 days without repo activity. If the repo goes quiet, re-enable it in the Actions tab (a push also resets the clock).
- Neon also has its own point-in-time restore on its free plan (short window). This backup is the longer-lived copy.
- A failed run emails the repo owner by default; leave notifications on.

Restore (to a new, empty Neon database, never over live data without a second copy):
```
# download the artifact zip from the Actions run and unzip it
pg_restore --no-owner --no-privileges -d "<new database direct URL>" backup-YYYY-MM-DD.dump
```
Use a `pg_restore` of the same version or newer as the dump. Then point `DATABASE_URL` at the restored database in Render.

## 8. Smoke test (task 69)
On your phone:
1. Open the app and install it to the home screen.
2. Log in.
3. Add a product with a photo.
4. Receive stock with a batch and expiry date.
5. Issue stock and confirm FEFO picked the earliest batch.
6. Open the Expiry page and confirm the batch appears.
7. Wait 20 minutes idle, reopen, and confirm the app wakes up and shows the loading message.

## 9. Troubleshooting
| Symptom | Likely cause |
|---|---|
| First request after idle is slow | Render or Neon cold start; expected |
| `too many connections` | Pool too large or direct (non-pooled) URL in use |
| Cookie not set in production | Missing `trust proxy` setting or `Secure` cookie without HTTPS |
| Images fail to upload | Wrong signature params or cloud name |
| Blank page on refresh of a sub-route | Missing catch-all route that returns `index.html` |
| Build fails on Render | Missing env var or wrong Node version (set `NODE_VERSION` if needed) |

Add `app.set('trust proxy', 1)` in Express, since Render sits behind a proxy.
